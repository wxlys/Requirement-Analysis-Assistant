【任务目标】

仅根据上述需求文档，生成可作为下一步测试用例生成输入的原子化测试点和待补充需求。

不得编写完整测试步骤，不得补充需求文档中未定义的业务规则、错误码、状态码、提示语、时间、阈值、权限、配置、性能指标或兼容环境。

【原子化规则】

1. 一个测试点对应一个独立测试规则或业务目标。
2. 同一规则的多个边界值可以合并，并在测试数据和预期结果中建立对应关系。
3. 不同输入字段、业务规则、权限角色、系统状态、安全目标、配置分支、异常处理方式或业务目标必须拆分。
4. 同一业务目标的多个必要断言可以保留在一个测试点中，例如登录成功同时校验 HTTP 200、业务码、凭证和会话。
5. 成功分支和失败分支、固定过期和闲置超时、网络异常和系统异常必须拆分。
6. 空字符串、空白字符串和缺失字段只有在需求明确等价时才可合并。
7. 禁用、锁定、未激活等不同账号状态必须分别生成测试点。
8. 条件必填参数必须覆盖条件未触发和已触发两种状态；条件未定义时也必须生成待补充测试点。

【需求编号】

1. 原文已有需求编号时必须沿用。
2. 原文没有编号时，按独立需求条目出现顺序生成 `REQ-模块-三位数字`。
3. **每个独立需求条目必须使用不同编号**：需求文档中每个独立的条款、章节条目、功能点、规则定义都是一个独立需求条目，各自分配唯一编号。编号数量应反映需求文档中独立需求条目的数量。
4. **严禁编号塌缩**：不得将所有测试点全部挂在同一个需求编号下。测试点数量多不代表需求编号只有一个；请先统计需求文档中的独立需求条目数量，再为每个条目分配编号。
5. 同一原始需求（同一个需求条目）可以对应多个测试点，但这些测试点共用该条目的同一个需求编号。
6. 不得为边界值、测试数据或测试点重复创建需求编号。
7. 每个测试点必须提供需求编号、需求章节和需求原文摘要。

【依据状态】

只能使用：

- 原文明确
- 原文推导
- 需求缺失
- 建议补充
- 待核对

【测试点状态】

只能使用：

- 可直接生成用例
- 待补充需求
- 暂不可测试

只有目标、依据、前置条件、测试数据、触发条件、预期结果和后置条件均明确，且不依赖未定义的错误码、状态码、时间、阈值、权限或配置时，才能标记为“可直接生成用例”。

如果测试点出现在任意 GAP 的 affectedTestPointIds 中，则不得标记为“可直接生成用例”。

【type 与 status 的区别】（重要）

- `type`（测试类型）与 `status`（测试点状态）是两个完全独立的字段，含义不同、取值集合不同。
- `type` 只能使用【优先级与类型】中列出的 11 种测试类型枚举：正向、反向、边界、状态转换、权限、安全、并发、性能、兼容性、异常恢复、数据完整性。
- `status` 只能使用本节列出的 3 种状态枚举：可直接生成用例、待补充需求、暂不可测试。
- **严禁将 status 的值（如"待补充需求"）填入 type 字段**；即使某测试点状态是"待补充需求"，它的 type 也必须从 11 种测试类型中选择。

【测试覆盖】

仅当需求文档明确涉及某测试维度时生成对应测试点；未定义的性能、兼容性、并发或第三方规则只生成待补充 GAP，不得虚构阈值或环境。

对需求中已涉及的内容，尽量覆盖：

- 正常、异常、边界和状态转换
- 空值、缺失、非法格式、非法类型和特殊字符
- 最小值、最大值和超限值
- 权限、越权、安全和凭证失效
- 重复提交、并发、异常恢复和数据完整性
- 性能、兼容性和第三方依赖

输入参数覆盖：

- 必填参数：合法值、空值、缺失值、非法格式、非法类型。
- 可选参数：缺省、合法值、非法值。
- 条件必填参数：未触发时缺省、已触发时缺省、已触发时合法值、已触发时非法值。
- 数值或长度参数：小于最小值、最小值、合法范围值、最大值、大于最大值。

需求明确提到的输入参数、请求来源、条件校验或安全校验，即使规则不完整，也必须生成对应的待补充测试点，不能只生成 GAP。

【预期结果】

1. 预期结果必须可观察、可判断，可包含状态码、业务码、提示、跳转、数据变化、权限、Token/会话、日志、响应时间、错误率或并发结果。
2. 不得使用“性能良好、系统稳定、操作方便、响应及时、权限正确、安全可靠、功能正常、处理成功”等模糊描述。
3. 预期结果不得使用“或、视情况、按配置、应该、结果正常、具体方式未定义、处理结果未定义”等不确定表达。
4. 如果需求未定义唯一结果，测试点必须标记为“待补充需求”或“暂不可测试”，并生成对应 GAP，不得自行选择结果。
5. 同一边界规则的多个数据可以合并，但必须明确不同数据对应的结果。

【输出格式】

只能输出合法 JSON，禁止输出 Markdown、代码围栏、解释、分析过程或额外文字。

顶层结构必须严格为：

{
  "testPoints": [],
  "gaps": []
}

testPoints 中每项必须严格包含以下字段：

  "requirementId": "REQ-LOGIN-001",
  "sourceSection": "第4节",
  "sourceSummary": "需求原文摘要",
  "module": "用户登录",
  "type": "正向",
  "name": "合法账号密码登录成功",
  "priority": "P0",
  "preconditions": [],
  "testData": [],
  "trigger": "提交登录请求",
  "expected": [],
  "postconditions": [],
  "evidenceStatus": "原文明确",
  "status": "可直接生成用例",
  "gapIds": [],
  "remarks": ""
}

gaps 中每项必须严格包含以下字段：

{
  "id": "GAP-001",
  "content": "缺失内容",
  "affectedTestPointIds": [],
  "impact": "对测试执行或预期结果的影响",
  "suggestion": "建议补充定义",
  "evidenceStatus": "需求缺失"
}

字段要求：

- id、requirementId、sourceSection、sourceSummary、module、name、trigger、remarks 必须是字符串。
- type、priority、evidenceStatus、status 必须使用规定枚举值。
- preconditions、testData、expected、postconditions、gapIds 必须是字符串数组。
- testPoints 和 gaps 必须是数组。
- 测试点编号、需求编号和 GAP 编号不得重复。
- 待补充测试点必须至少关联一个 gapId。
- 可直接生成用例的测试点 gapIds 必须为空。
- 每个 gap 的 affectedTestPointIds 必须引用真实存在的测试点。
- GAP 只能关联真正受其缺失内容影响的测试点，不得按功能模块扩大关联范围。
- 如果缺失内容不影响测试点核心预期，不得关联该测试点。

【优先级与类型】

priority 只能使用 P0、P1、P2：

- P0：核心流程、安全、数据正确性或高风险功能。
- P1：重要功能、异常流程、边界流程或主要权限规则。
- P2：一般功能、低风险功能或体验类内容。

type 只能使用（11 种，缺一不可）：

- 正向
- 反向
- 边界
- 状态转换
- 权限
- 安全
- 并发
- 性能
- 兼容性
- 异常恢复
- 数据完整性

【最终检查】

输出 JSON 前必须确认：

1. JSON 可被标准解析器直接解析。
2. 只包含 testPoints 和 gaps 两个顶层字段。
3. 所有必填字段存在且类型正确。
4. 所有枚举值合法，所有编号唯一。
5. **type 必须是 11 种测试类型之一，绝不能用"待补充需求"等状态值充当 type。**
6. **需求编号覆盖完整性**：统计需求文档中独立需求条目的数量，检查生成的 requirementId 种类数是否与之相当；全部测试点只用 1 个 requirementId 属于编号塌缩错误，必须避免。
7. 同一原始需求只使用一个需求编号。
8. 不同字段、角色、状态、配置分支和不同业务结果已拆分。
9. 空字符串、空白字符串和缺失字段未明确等价时已拆分。
10. 条件必填参数已覆盖未触发和已触发状态。
11. 预期结果没有模糊或不确定表达。
12. 需求缺失、推断和待核对内容未标记为原文明确。
13. 所有待补充测试点都有 GAP。
14. 所有 GAP 影响的测试点都不是可直接生成用例状态。
15. 未定义的性能、兼容性、并发或第三方规则没有被虚构。
16. 不输出 JSON 之外的任何内容。
